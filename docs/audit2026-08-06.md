# Security Audit — Incoming SMS Gateway (tech.bogomolov.incomingsmsgateway)

Date: 2026-08-06
Scope: PII leaking to third parties other than the user-configured webhook URL.
Audit lens: adversarial — assume WiFi/ISP are hostile, Google cloud is a third party,
and other installed apps are untrusted.

## Data inventory (what the app handles)

| Data | Where stored | Where it goes |
|---|---|---|
| SMS body + sender | In-flight worker `Data`, SharedPreferences `activity_log` (new), `failed_messages` | Webhook POST to configured URL; **Google Drive backup**; **network transit** |
| Webhook URLs, custom headers, HMAC secret | SharedPreferences `phones` (or `телефоны` on Russian locale) | Webhook request headers; **Google Drive backup** |
| Heartbeat URL | SharedPreferences `heartbeat` | Ping to configured URL; **Google Drive backup** |
| Device health (`%battery% %network% %power% %version%`) | — | Only embedded in payload if template uses them → configured URL |
| Prepared JSON payloads | WorkManager DB (`androidx.work.workdb`) | **Google Drive backup** |

Outbound network = webhook URL + heartbeat URL only. No analytics, ads, crash-reporting,
or telemetry SDKs (deps are androidx / material / navigation / work / commons-text).

## Findings

### CRITICAL — F1: Android Auto Backup / Device Transfer exfiltrates SMS bodies and secrets to Google cloud

- **Location:** `app/src/main/AndroidManifest.xml:16` (`android:allowBackup="true"`, no `fullBackupContent` / `dataExtractionRules`)
- **Domain:** Secrets / Blast radius / Info disclosure
- **Detail:** Auto Backup (API 23–30) and device-to-device transfer (API 31+) back up the
  app sandbox by default: every SharedPreferences file and database. That includes:
  - `phones` / `телефоны` — webhook URLs, custom headers, HMAC-SHA-256 secrets
  - `failed_messages` — full prepared JSON payloads containing SMS bodies
  - `activity_log` — SMS bodies (added for the log feature)
  - `heartbeat` — heartbeat URL
  - `androidx.work.workdb` — WorkManager input `Data` carrying `DATA_TEXT` (prepared payload)
    and `DATA_CONTENT` (raw SMS body) for every queued/in-flight delivery
- **Impact:** Full SMS conversation history, webhook credentials, and HMAC secrets are
  copied to Google Drive / a new device outside the user's control — the single largest
  PII and secret leak, entirely unrelated to the configured webhook URL.
- **PoC (physical):**
  ```
  adb backup -f backup.ab -noapk tech.bogomolov.incomingsmsgateway
  # decrypt/unescape with abe.jar, then read the extracted
  # shared_prefs/activity_log.xml and shared_prefs/failed_messages.xml
  ```
  Rooted device: `adb shell su -c 'cat /data/data/tech.bogomolov.incomingsmsgateway/shared_prefs/activity_log.xml'`.
  Cloud: any auto-backup trigger → google.com/backup restore yields the same files.
- **Fix:** Add `res/xml/backup_rules.xml` (and `data_extraction_rules.xml` for API 31+)
  excluding `activity_log`, `failed_messages`, `phones`, `телефоны`, `heartbeat`, and
  `androidx.work.workdb` (or set `android:allowBackup="false"` — simplest and safest for
  a privacy-forwarding app).

### HIGH — F2: Cleartext HTTP + optional trust-all SSL expose SMS bodies to network observers

- **Location:** `app/src/main/AndroidManifest.xml:22` (`usesCleartextTraffic="true"`);
  `Request.java:143-150` (`TLSSocketFactory(ignoreSsl)` + `AllowAllHostnameVerifier`);
  `app/src/main/java/tech/bogomolov/incomingsmsgateway/SSLSocketFactory/TLSSocketFactory.java`
- **Domain:** HTTP controls / Crypto / Transport
- **Detail:** Any rule configured with `http://` transmits the full SMS body and custom
  headers in plaintext. Even with `https://`, enabling per-rule "Ignore SSL/TLS errors"
  installs a trust-all socket factory + allow-all hostname verifier, so anyone able to
  terminate the connection (WiFi portal, captive proxy, ISP, DNS-impersonating network)
  can read every forwarded SMS. This is deliberate (CLAUDE.md documents it for local/LAN
  endpoints) but is a direct third-party PII channel.
- **PoC:** `sudo tcpdump -A -i en0 'tcp port 80'` on the same LAN → full POST bodies readable;
  or a MITM proxy for an ignore-SSL `https://` endpoint.
- **Fix:** Make cleartext opt-in per rule already exists; consider a UI warning when the
  rule URL is `http://` or ignore-SSL is on; keep the ignore-SSL path off by default
  (already is).

### HIGH — F3: HTTP redirects re-send PII (and headers) to an origin other than the configured URL

- **Location:** `Request.java:61` (HttpURLConnection created with default
  `instanceFollowRedirects=true`; `execute()` `Request.java:163-190` does not disable or
  re-validate redirects)
- **Domain:** SSRF / HTTP controls
- **Detail:** `HttpURLConnection` follows redirects automatically. A configured URL that
  returns 301/302/303 re-sends the request (headers intact, including custom headers and
  the `X-Signature` HMAC; body dropped on GET-conversion) to the redirect target; 307/308
  re-sends the full body too. So a misconfigured or compromised endpoint can funnel the
  SMS payload to an attacker-controlled third party while the user believes it only ever
  hit their own URL.
- **PoC:** Configure URL to `https://host.example/redirect` that responds `307 Location:
  https://attacker.in/collect`; the full prepared payload and custom headers arrive at the
  attacker.
- **Fix:** `connection.setInstanceFollowRedirects(false)` (fail the request on a 3xx
  instead of silently retargeting), or allow only same-host redirects.

### MEDIUM — F4: Exported foreground service is startable by any app

- **Location:** `app/src/main/AndroidManifest.xml:24-26` (`android:exported="true"` on `.SmsReceiverService`)
- **Domain:** Blast radius / availability
- **Detail:** Any installed app (all hold the install-time `FOREGROUND_SERVICE`
  permission) can call `startForegroundService` on this service, forcing the persistent
  "F" notification and starting the heartbeat thread. On modern Android background-start
  limits blunt it, but it still lets an unrelated app hijack the status-bar indicator and
  spin up the heartbeat scheduler. No PII leaves the device, but it is an unnecessary
  external attack surface.
- **Fix:** `android:exported="false"` (nothing external legitimately starts it).

### LOW — F5: URL with embedded credentials appears in logcat

- **Location:** `Request.java:190` (`Log.e(... URL)`, `Request.java:55` malformed-URL log)
- **Domain:** Log exposure
- **Detail:** If a user configures `https://user:pass@host/hook`, the URL (with basic-auth
  credentials) is written to logcat and visible via the in-app Syslog viewer / `adb logcat`.
  Low likelihood; no bodies or tokens logged elsewhere (verified: no log call includes the
  message body).
- **Fix:** Strip userinfo from URLs before logging.

## Passed (no issue)

- No analytics / ads / crash-reporting / telemetry SDKs — no third-party call-home besides
  the configured webhook and heartbeat URLs.
- Manifest SMS receiver is guarded by `android:permission="android.permission.BROADCAST_SMS"`
  (system-only), so no app can spoof SMS into the forwarder.
- `logcat` output contains no SMS bodies (regex patterns and response codes only).
- `ActivityLogActivity`, `SettingsActivity` are `exported="false"`.
- `%version%/%battery%/%power%/%network%` device-health data is sent only when the template
  opts in and only to the configured URL.
- `READ_SMS` is requested only for the explicit, user-initiated backfill.

## Priority

1. F1 (backup exfiltration) — fix before any release; biggest exposure.
2. F3 (redirects) — one-line hardening; closes an active third-party funnel.
3. F2 (cleartext/ignore-SSL) — product trade-off; at least warn in UI.
4. F4 (exported service), F5 (URL logging) — hygiene.

All findings are PII/secret leak vectors to parties other than the configured URL; none
require the configured endpoint to be malicious beyond standard misconfiguration/redirect.
